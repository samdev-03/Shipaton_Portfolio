# Operations and security boundaries

This release is designed for a single persistent Node 24 process using SQLite WAL. The worker runs every 15 seconds and prevents overlapping ticks. Database writes use transactions where several records must change together; tasks and rehearsal turns check versions. Running multiple independent SQLite replicas is unsupported. Scale by migrating the storage/queue layer before introducing multiple instances.

Content is encrypted with AES-256-GCM. Some operational fields, such as task status, app IDs and timestamps, remain plaintext. Passwords use scrypt with a random salt; session and recovery tokens are stored as hashes. API sessions expire after 30 days. An account email is a login identifier, not verified identity. Password recovery requires the saved high-entropy recovery code; a reset revokes all existing sessions and rotates that code. An operator must not override recovery based on an unverified email alone.

API requests are bounded and rate limited. All SQL values are bound parameters. Web sessions use HttpOnly, SameSite cookies; production adds Secure and the __Host prefix. Allowed origins must be exact. Public approval links are bearer capabilities: anyone with a link can see/approve its quote, so use revocation after accidental sharing. Acceptance records a typed name and timestamp, not verified identity or a legal-signature guarantee.

Deploy behind TLS with persistent disk, disk encryption and access controls. Verify firewall/proxy setup; keep `/ops/*` off public indexes and protect OPS_TOKEN. Logs generated by this app contain request IDs and error classes rather than request bodies; check reverse-proxy/host logging separately. Monitor 5xx rate, latency, disk space, /readyz, failed reminders and deletion queue age. Provider outages preserve free features when possible; premium requests fail closed if authoritative access cannot be obtained. Entitlements may be cached for up to five minutes.

Back up using `node --env-file=.env scripts/backup.mjs <protected-destination.sqlite>`. Do not copy a live SQLite file without its WAL consistency. The script uses SQLite's online backup API. Store backups encrypted in a separate location and keep DATA_KEY independently. Proposed starting policy: daily backups, seven-day retention and weekly restore drills. This is not an automatic policy: configure the scheduler, cleanup and encryption in your deployment and update the public privacy policy to the actual values. After restore, re-apply any deletions made since the backup and reconcile provider state before enabling writes.

The current Render disk receives automatic daily encrypted snapshots. Render documents availability for **at least** seven days, not a guaranteed seven-day maximum expiry. Use `BACKUP_RETENTION_POLICY` to state that provider-managed behavior accurately; do not set `BACKUP_RETENTION_DAYS=7` as an unverified maximum. Reference: https://render.com/docs/disks (checked September 26, 2026). A tested SQLite backup/restore procedure remains required before claiming disaster-recovery readiness.

Account deletion removes active account records and owned circles, resets unfinished assigned tasks in other circles, and queues RevenueCat/OneSignal deletion. Layers requests are retained for manual handling. Provider failures retry; monitor and escalate prolonged failures. Billing records retained by stores or payment processors are governed by those providers' obligations and policies. Deleting an app account does not cancel its store subscription.

AI calls require explicit consent and Pro. Text requests use structured output and `store:false`; audio has an 8 MiB server cap and 60-second client cap. The server does not write recordings to disk. Temporary client files are removed after processing or cancellation; independently test OS interruption behavior on native devices. Explain provider retention accurately, without claiming zero retention. Guided wording cues are transparent heuristics, not validated psychological or employment scores.

Recovery after a service incident: stop admission of new writes if integrity is uncertain; preserve restricted diagnostic evidence; restore a tested snapshot to an isolated environment; verify schema and core flows; reconcile entitlements/deletions; reopen traffic and document the incident. No production incident-response or privacy-compliance certification is claimed.
